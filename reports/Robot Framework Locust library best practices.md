# Build robotframework-locust with a hybrid core and lazy Locust imports

The best-practice path for robotframework-locust is a HybridCore library (robotlibcore) that exposes component classes for Users, LoadTest, and Stats, backed by a src-layout Python package, lazy Locust imports, and a single keyword that owns the entire gevent-driven run. Locust's monkey-patching and greenlet model demand that the library never let Robot Framework touch Locust state across threads, so the plan must center on one blocking run keyword, cooperative cancellation, and post-run stats thresholds rather than streaming parallelism.

## Drive Locust from one keyword that owns the whole run

Locust is fully drivable from Python through `Environment` plus a local/master/worker `Runner`, with lifecycle controlled by `runner.start`, `runner.greenlet.join`, and `runner.quit`, and hooks exposed via `events.init`, `events.test_start`, `events.test_stop`, and `events.quitting` ([Locust use-as-lib](https://docs.locust.io/en/stable/use-as-lib.html)). A Robot Framework keyword should build the `Environment`, run it to completion, then read `environment.stats.total` and raise on threshold violations, because Robot Framework is not thread-safe and Locust's greenlets are not RF-safe ([RF forum multithreading](https://forum.robotframework.org/t/robot-framework-multithreading/5050)). Dynamic User subclasses are created with `type("RFUser", (HttpUser,), {"host": host, "tasks": [task_fn]})`, with tasks kept as module-level functions rather than closures capturing RF state, and `abstract=True` bases excluded from spawning ([Locust writing-a-locustfile](https://docs.locust.io/en/stable/writing-a-locustfile.html)). The run keyword should set `environment.process_exit_code` in an `@events.quitting` listener based on `fail_ratio`, `avg_response_time`, and `get_response_time_percentile(0.95)` ([running-without-web-ui](https://docs.locust.io/en/2.30.0/running-without-web-ui.html)).

## Patch gevent early and keep task functions non-blocking

Locust calls `gevent.monkey.patch_all()` on import unless `LOCUST_SKIP_MONKEY_PATCH=1` is set, and because every virtual user is a cooperative greenlet on one OS thread, blocking or CPU-bound work stalls all users ([Locust use-as-lib](https://docs.locust.io/en/stable/use-as-lib.html); [gevent monkey docs](http://www.gevent.org/api/gevent.monkey.html)). The library should import Locust as early as possible or set the skip variable and patch manually at the top of the RF entry point, and task functions must avoid heavy CPU or C-extension I/O such as unpatched database drivers ([Tarragon knowledge card](https://tarrragon.github.io/blog/backend/knowledge-cards/gevent-monkey-patching)). For multi-core load generation, prefer multiple worker processes via `--processes` rather than threads ([Tarragon](https://tarrragon.github.io/blog/backend/knowledge-cards/gevent-monkey-patching)). Python 3.11 compatibility requires greenlet 3.0+ ([Celery gevent docs](https://docs.celeryq.dev/en/stable/userguide/concurrency/gevent.html)).

## Package as a modern src-layout library with lazy heavy imports

Use a single `pyproject.toml` with a `[build-system]` table, PEP 639 SPDX license expression, `[dependency-groups]` for dev tools, and `requires-python = ">=3.11"` ([packaging.python.org](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/)). Place the package under `src/`, single-source the version dynamically, build sdist plus wheel with `python -m build`, and publish through trusted publishing via `pypa/gh-action-pypi-publish` ([packaging.python.org](https://packaging.python.org/en/latest/guides/publishing-package-distribution-releases-using-github-actions-ci-cd-workflows/)). Pin `locust>=2.30,<3` and `greenlet>=3.0`, declare ranges with major-version bounds, commit a `uv.lock` with hashes, and lazy-import Locust inside keywords so `--dryrun` and import stay fast ([DjangoZen packaging guide](https://www.djangozen.com/tutorials/packaging-python-for-production-uv-pyproject-wheels-lockfiles-and-private-indexes/)). For Robot Framework packaging, name it `robotframework-locust`, add the `Framework :: Robot Framework` classifier, and expose it as a pip-installable library ([RF User Guide distributing](https://robotframework.org/robotframework/latest/RobotFrameworkUserGuide.html#distributing-test-libraries)).

## Structure the library as HybridCore components with RF-safe state

Choose the Hybrid API through robotlibcore (`DynamicCore`/`HybridCore`) so components such as Users, LoadTest, and Stats can own their concerns while metadata comes through `@keyword` and optional `get_keyword_arguments` ([PythonLibCore README](https://github.com/robotframework/PythonLibCore/blob/main/README.md)). Default library scope is TEST, but a long-running load test needs SUITE or GLOBAL scope with an explicit reset/cleanup keyword, while keeping all Locust calls on the main thread ([RF User Guide Creating test libraries](https://robotframework.org/robotframework/latest/RobotFrameworkUserGuide.html#creating-test-libraries)). Add type hints to every keyword parameter for RF 7.0+ automatic conversion, document arguments, returns, and exceptions in RF-formatted docstrings, and use `@keyword(tags=...)` for categorization ([RF User Guide creating keywords](https://robotframework.org/robotframework/latest/RobotFrameworkUserGuide.html#creating-keywords)). Avoid module-level mutable state and use `robot.api.logger` instead of print, with idempotent cleanup between tests.

## Export stats and reports after the run completes

After the run, read `environment.stats.total` for `num_requests`, `num_failures`, `avg_response_time`, `min/max_response_time`, `median_response_time`, `total_rps`, `current_rps`, `fail_ratio`, `get_response_time_percentile(p)`, and `stats.errors` for failure details ([stats source](https://docs.locust.io/en/latest/_modules/locust/stats.html)). For CSV output, instantiate `StatsCSVFileWriter` and spawn a greenlet to write periodically, or generate files after the run; for HTML, call `get_html_report()` or the web UI `/stats/report` endpoint ([retrieving-stats](https://docs.locust.io/en/stable/retrieving-stats.html); [DeepWiki](https://deepwiki.com/locustio/locust/2.3-statistics-and-reporting)). In CI and Robot Framework automation, prefer headless programmatic mode and expose the optional web UI on a configured port only for debugging ([running-without-web-ui](https://docs.locust.io/en/2.30.0/running-without-web-ui.html)).

## Test at two levels and gate with strict tooling

Unit-test Python logic with pytest, parametrization, and fixtures under `conftest.py`, enforce an 80% coverage minimum, and run acceptance tests as `.robot` suites exercising the keywords ([Python tooling stack 2026](https://pythonresources.com/guides/python-tooling-stack-2026/); [RF User Guide](https://robotframework.org/robotframework/latest/RobotFrameworkUserGuide.html)). Use pabot for parallel execution and run Robot repos in the Alpine CI image on a clean `git archive` before pushing. Lint and format with Ruff using `extend-select` (never replacing defaults), type-check with mypy strict plus overrides ignoring missing imports for locust and robotframework, and run pip-audit, bandit, and detect-secrets in CI ([Ruff settings](https://docs.astral.sh/ruff/settings/); [Python security tools 2026](https://safeguard.sh/resources/blog/python-security-tools)).

## Conclusion

The plan should be adjusted to treat robotframework-locust as a single-owner-run library rather than a thin Locust wrapper: one blocking keyword owns the gevent lifecycle, stats thresholds decide pass/fail, and all RF state stays on the main thread. Packaging, testing, and CI then follow the 2026 Python standard with lazy imports, strict typing, and Alpine-verified Robot acceptance tests. The remaining uncertainty is the exact Locust version pinned and the precise `StatsCSVFileWriter` signature, both of which must be verified against the installed 2.30+ release before release.
