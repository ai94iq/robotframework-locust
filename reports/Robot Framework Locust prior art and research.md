# Prior Art Reveals a Locust-First, Process-Isolated Design

No dedicated robotframework-locust package exists on PyPI or GitHub, so the design should treat Locust as the outer driver and Robot Framework as the per-user workload, with process isolation as the safe default and in-process invocation left unverified. The strongest precedent is rfswarm, which runs real Robot test cases across agents with ramp-up, per-robot variable injection, and a manager/agent/reporter split, while eficode's robotframework-oxygen wraps Locust headless runs via a BaseHandler and parses CSV into RF-friendly results. In-process `robot.run` inside a Locust HttpUser task is documented to collide on Chrome and global state, and the only reported working fix is `subprocess.Popen(['robot', ...])` per virtual user. Locust's own library API (`Environment`, `create_local_runner`, `spawn_users`) could in principle enable in-process RF per user, but no source tests that combination, so it should be treated as an unverified risk rather than a plan. License compatibility also bites: rfswarm is GPL-3.0 and cannot be reused in an Apache-2.0 RF library without checking terms.

The academic research converges on three design implications for a Locust-based tool: open-loop request generation to avoid coordinated omission, warmup exclusion and hysteresis in health assessment, and percentile-and-change-point-based regression detection instead of mean comparisons. Vanguard (Meta) is the headline reference, an adaptive load-testing framework with feedback-driven search, dampening (alpha=0.5), spike tolerance (tau=2), convergence detection via coefficient of variation over the last three capacity estimates, and open-loop generation; it cut MAE from 42.1% (naive linear scaling) to 5.2% with workload calibration reducing estimation error from ~30% to 2-6% and warmup handling improving accuracy by 22.2%. Its health assessment uses five states (Healthy/Warn/Unhealthy/Critical/Overloaded) with a weighted score and hysteresis (n=2 windows upward, n=3 downward), reporting ~40% false-positive reduction. Mesh2 integrates Locust as the primary distributed load generator for Kubernetes resilience evaluation, confirming Locust's status as the de-facto reference generator in academic work. RELOAD (RL-driven) and LLMRunner (closed-workload LLM serving) round out the landscape but are not directly applicable to RF workloads.

Statistical rigor for pass/fail decisions should follow the regression-detection literature, which favors change-point detection on time series, bootstrap confidence intervals, non-parametric tests, and tail percentiles (P90/P99) over mean-based comparisons, with sustained-violation (hysteresis) rules to prevent flapping. A single performance test run can mislead on a 10% difference, so a single Locust run should not gate a release without repeated or windowed evidence. Vanguard's use of non-parametric tests, ICC for reproducibility, Bland-Altman for agreement, and 95% bootstrap CIs over 10,000 resamples is the most concrete methodological template available. Warmup-to-steady transition detection (steady-state kernel approach) is directly relevant because Locust runs have a ramp-up phase that contaminates early latency samples.

Concurrency reality imposes a hard ceiling: gevent greenlets are cooperative and single-threaded, so CPU-bound work (JSON processing, heavy user code) stalls every virtual user, the hub greenlet must never perform I/O, and the GIL limits multi-core utilization in one process. Greenlet 3.3+ supports free-threaded CPython but only with limited testing, and high-QPS client-side GIL contention is a measurable limiter independent of server capacity. For scaling, prefer multiple worker processes (Locust `--processes` or rfswarm-style agents) over threads, and treat Python 3.13+ free-threaded builds as experimental. No peer-reviewed benchmark quantifies greenlet overhead versus asyncio/trio for load generation, so any performance claim about the chosen concurrency model should be labeled unverified.

Packaging and library structure should follow the modern RF ecosystem: `src/` layout with `pyproject.toml`, PEP 639 SPDX license, `[dependency-groups]` for dev tools, trusted publishing via OIDC, and lazy imports of heavy deps via module-level `__getattr__` (PEP 562) so `import` stays fast and `--dryrun` avoids pulling Locust. PythonLibCore (`HybridCore`/`DynamicCore`, v4.6.0, ~298k weekly downloads) is the canonical component-class pattern, used by SeleniumLibrary and Browser library, with keywords decorated via `@keyword` and aggregated through `library_components`. No concrete locust-Robot hybrid example exists on GitHub, so the pattern must be adapted. Optional GUI extras should follow the PySide6 convention (asammdf, superqt, gratinglab): keep the core Qt-free, guard imports with try/except raising a helpful ModuleNotFoundError, and use qt-material for theming plus pyqtgraph (50-60 fps, <10 ms latency) for live metrics, with PyInstaller or pyside6-deploy for standalone builds.

The remaining gaps and risks are concrete and should drive the first implementation decisions. There is no direct arXiv comparison of Locust versus k6/JMeter on identical workloads, so relative-performance claims are vendor-sourced. No arXiv paper benchmarks Locust master/worker scaling limits (max users per worker, network overhead). No canonical statistical test for performance regression across heterogeneous workloads exists, so method choice stays context-dependent. Locust-as-library in-process RF invocation is unverified against RF global-state isolation. rfswarm is GPL-3.0 and unusable as code in an Apache-2.0 library. No RF library combines Locust with a Qt GUI, and no token-based design system (spacing/typography) beyond colors was found in the surveyed theming libraries. Finally, no RF library demonstrates HybridCore component decomposition beyond SeleniumLibrary and Browser, so the component split for a load-testing library is novel territory. The safest path is to ship a CLI/RF-only core first, wrap Locust headless runs with CSV parsing in the Oxygen style, gate pass/fail on P90/P99 thresholds with sustained-violation rules, and leave GUI and in-process modes as explicitly unverified options.

## Conclusion

The research points to a clear, conservative design: Locust owns load generation, Robot Framework owns test cases, and process isolation owns safety, with adaptive metrics and percentile-based thresholds layered on top.
